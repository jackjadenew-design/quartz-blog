# 驾驭工程：在智能体优先的世界中运用 Codex

**作者：** Ryan Lopopolo，技术人员  
**日期：** 2026 年 2 月 11 日  
**原文：** https://openai.com/index/harness-engineering/

---

过去五个月，我们团队一直在进行一项实验：用 **零行手工编写代码** 来构建并发布一款软件产品的内部测试版。

这款产品已有内部日常用户和外部 alpha 测试者。它上线、部署、出故障、再修复——一切如常。与众不同的是，每一行代码——应用逻辑、测试、CI 配置、文档、可观测性配置以及内部工具——全部由 Codex 编写。我们估计，完成这些工作所花的时间大约是手工编写代码所需时间的十分之一。

**人类掌舵，智能体执行。**

我们故意设置了这一约束，以迫使自己构建出真正能将工程效率提升数个数量级的系统。我们只有数周时间来交付最终超过百万行代码的产品。为此，我们必须弄清楚：当软件工程团队的首要工作不再是写代码，而是设计环境、明确意图、建立反馈回路以让 Codex 智能体可靠运作时，究竟会发生什么变化。

这篇文章记录的，正是我们与一支智能体团队共同构建全新产品的过程中所学到的一切——哪里出了问题、哪里产生了复利效应，以及如何最大化利用我们唯一真正稀缺的资源：**人类的时间与注意力**。

---

## 我们从一个空的 Git 仓库起步

第一次提交落在 2025 年 8 月下旬，那时仓库还是一片空白。

最初的脚手架——仓库结构、CI 配置、格式化规则、包管理器设置和应用框架——由 Codex CLI 使用 GPT-5 生成，以少量现有模板为参照。就连指导智能体如何在仓库中工作的初始 AGENTS.md 文件，本身也是由 Codex 编写的。

系统里没有任何预先存在的人工编写代码作为基础。从一开始，仓库的形态就由智能体塑造。

五个月后，仓库已包含约百万行代码，涵盖应用逻辑、基础设施、工具链、文档和内部开发者工具。在这一过程中，一支仅有三名工程师的小团队驱动 Codex 开启并合并了约 1500 个 Pull Request，平均每位工程师每天处理 3.5 个 PR。令人意外的是，随着团队扩充至七名工程师，吞吐量还在持续提升。重要的是，这些产出绝非为了产出而产出——这款产品已在内部被数百名用户使用，其中不乏每日高频的内部核心用户。

整个开发过程中，人类从未直接贡献过任何代码。这成为了团队的核心理念：**不编写任何手工代码**。

---

## 重新定义工程师的角色

没有人工直接编码，带来了一种截然不同的工程工作形态，工作重心转向了系统设计、脚手架构建和杠杆放大。

早期进展比我们预期的要慢，但原因不在于 Codex 能力不足，而在于**环境定义不够充分**。智能体缺乏向高层目标推进所需的工具、抽象层和内部结构。我们工程团队的首要工作，由此变成了**让智能体能够做有价值的工作**。

在实践中，这意味着采用深度优先的方式：将更大的目标拆解为更小的构建块（设计、编码、审查、测试等），提示智能体逐块完成，再以此解锁更复杂的任务。当某件事失败时，解法几乎从来不是"再努力一点"。因为推动进展的唯一方式是让 Codex 完成工作，人类工程师在介入时始终会问：**"缺少什么能力？如何让它对智能体既可理解又可强制执行？"**

人类与系统的交互几乎完全通过提示词进行：工程师描述一项任务，运行智能体，让它提交 Pull Request。为了将 PR 推进到完成，我们会指示 Codex 在本地审查自身的改动，在本地和云端请求其他专项智能体审查，回应人类或智能体的反馈，并循环迭代，直到所有智能体审查者满意为止（本质上是一个"拉尔夫·威格姆循环"）。Codex 直接使用我们的标准开发工具（gh、本地脚本和仓库内嵌技能）收集上下文，无需人工复制粘贴到命令行。

人类可以审查 Pull Request，但并非必须。随着时间推移，我们已将几乎所有审查工作推向**智能体对智能体**的模式处理。

## 提升应用可读性

随着代码吞吐量的提升，瓶颈转移到了人工 QA 环节。由于固定约束始终是人类的时间与注意力，我们致力于让应用 UI、日志和应用指标本身对 Codex 直接可读，以此为智能体赋予更多能力。

例如，我们让应用可以按 git worktree 独立启动，这样 Codex 就能为每个变更各自启动并驱动一个应用实例。我们还将 Chrome DevTools Protocol 接入了智能体运行时，并创建了用于处理 DOM 快照、截图和页面导航的技能模块。这使 Codex 能够直接复现 Bug、验证修复效果，并对 UI 行为进行推理。

可观测性工具亦然。日志、指标和追踪数据通过一套为每个 worktree 临时搭建的本地可观测性栈暴露给 Codex。Codex 在一个完全隔离的应用实例上工作——包括其日志和指标——任务完成后即被销毁。智能体可以用 LogQL 查询日志，用 PromQL 查询指标。有了这些上下文，"确保服务启动在 800 毫秒内完成"或"这四条关键用户旅程中没有任何 span 超过两秒"之类的提示便成为了可操作的目标。

我们经常看到单次 Codex 运行在一项任务上持续工作超过六小时（通常是在人类熟睡时）。

## 将仓库知识设为记录系统

上下文管理是使智能体在大型复杂任务中发挥效能的最大挑战之一。我们最早学到的一课很简单：**给 Codex 一张地图，而不是一本千页的操作手册**。

我们尝试过"一个大型 AGENTS.md"的方案，结果以可预见的方式失败了：

- **上下文是稀缺资源。** 一个巨大的指令文件会挤占任务、代码和相关文档的空间——智能体要么忽略关键约束，要么开始为错误的目标优化。
- **过多的指导变成了无效指导。** 当所有事情都"重要"时，就没有什么真正重要了。智能体最终会进行本地模式匹配，而非有意识地导航。
- **它立即腐烂。** 一个单体手册会变成一堆过时规则的坟场。智能体无法判断哪些内容仍然有效，人类也停止维护它，文件悄然成为一个有害的存在。
- **难以验证。** 单一的文档块不适合进行机械化检查（覆盖率、新鲜度、所有权、交叉链接），因此偏差不可避免。

因此，我们不再将 AGENTS.md 视为百科全书，而是将其视为**目录**。

仓库的知识库存放在一个结构化的 `docs/` 目录中，作为记录系统。一个简短的 AGENTS.md（约 100 行）被注入上下文，主要充当地图的角色，指向其他地方更深层的信息源。

```
AGENTS.md
ARCHITECTURE.md
docs/
├── design-docs/
│   ├── index.md
│   ├── core-beliefs.md
│   └── ...
├── exec-plans/
│   ├── active/
│   ├── completed/
│   └── tech-debt-tracker.md
├── generated/
│   └── db-schema.md
├── product-specs/
│   ├── index.md
│   ├── new-user-onboarding.md
│   └── ...
├── references/
│   ├── design-system-reference-llms.txt
│   ├── nixpacks-llms.txt
│   ├── uv-llms.txt
│   └── ...
├── DESIGN.md
├── FRONTEND.md
├── PLANS.md
├── PRODUCT_SENSE.md
├── QUALITY_SCORE.md
├── RELIABILITY.md
└── SECURITY.md
```

*仓库内知识库目录结构。*

设计文档经过分类和索引，包含验证状态和一套定义智能体优先操作原则的核心信念。架构文档提供了业务领域和包分层的顶层视图。一份质量文档对每个产品域和架构层进行评级，并随时间追踪差距。

计划被视为一等公民。轻量级的临时计划用于小型改动，而复杂工作则以执行计划的形式捕获，包含进度和决策日志，并提交到仓库中。活跃计划、已完成计划和已知技术债务全部进行版本控制并集中存放，使智能体无需依赖外部上下文即可运作。

这实现了**渐进式披露**：智能体从一个小而稳定的入口点开始，并被告知接下来应在何处查找，而非一开始就被信息淹没。

我们以机械化方式强制执行这一结构。专用的 linter 和 CI 任务验证知识库是否最新、交叉链接是否正确、结构是否规范。一个定期运行的"文档园丁"智能体会扫描那些不再反映真实代码行为的陈旧或过时文档，并提交修复 PR。

## 智能体可读性是目标

随着代码库的演进，Codex 做设计决策的框架也需要随之演进。

由于仓库完全由智能体生成，它首先为 Codex 的可读性而优化。正如团队会为新入职的工程师提升代码的可导航性，我们人类工程师的目标是让智能体能够直接从仓库本身推理出完整的业务领域。

从智能体的视角来看，任何在运行时无法在上下文中访问的内容，实际上都不存在。存在于 Google Docs、聊天记录或人们脑海中的知识，对系统来说都无从访问。仓库本地的版本化产物（如代码、Markdown、Schema、可执行计划）才是它所能看到的一切。

我们逐渐意识到，需要不断将更多上下文推入仓库。那次让团队在架构模式上达成共识的 Slack 讨论？如果智能体无法发现它，这段知识就像三个月后才入职的新人所不了解的事情一样，对智能体而言毫无意义。

给 Codex 更多上下文，意味着组织和暴露正确的信息，让智能体能够对其进行推理，而非用临时指令淹没它。就像你会向新队友介绍产品原则、工程规范和团队文化（包括 emoji 偏好）一样，向智能体提供这些信息会带来更符合预期的输出。

这一思维框架厘清了许多权衡。我们倾向于选择那些能够在仓库内被完全内化和推理的依赖与抽象。通常被描述为"无聊"的技术往往更容易被智能体建模，因为它们具有更好的可组合性、更稳定的 API，以及在训练集中更充分的表示。在某些情况下，让智能体重新实现部分功能，比绕过公共库中不透明的上游行为更为经济。例如，我们没有引入通用的 p-limit 风格的包，而是实现了自己的 map-with-concurrency 工具函数：它与我们的 OpenTelemetry 监控深度集成，测试覆盖率达 100%，且行为完全符合我们运行时的预期。

将更多系统纳入智能体可检查、可验证、可直接修改的形态，能够放大杠杆——不仅对 Codex，对其他也在代码库上工作的智能体（如 Aardvark）同样如此。

## 强制执行架构与品味

仅靠文档无法让一个完全由智能体生成的代码库保持内聚。通过强制执行不变量而非微观管理实现细节，我们让智能体能够快速交付，同时不破坏基础。例如，我们要求 Codex 在边界处解析数据结构，但对具体实现方式不作规定（模型似乎偏爱 Zod，但我们并没有指定这个具体的库）。

智能体在边界严格、结构可预测的环境中效率最高，因此我们围绕一个刚性架构模型构建了应用。每个业务领域被划分为固定的分层集合，依赖方向经过严格验证，允许的边仅有有限几种。这些约束通过自定义 linter（当然，也是由 Codex 生成的！）和结构测试进行机械化强制执行。

规则如下：在每个业务领域内（如应用设置），代码只能沿固定的分层序列"向前"依赖：

**Types → Config → Repo → Service → Runtime → UI**

横切关注点（认证、连接器、遥测、功能开关）通过唯一的显式接口进入：**Providers**。其他任何方式均被禁止，并通过机械化手段强制执行。

这是你通常会推迟到拥有数百名工程师才会着手的架构。而使用编码智能体时，它是一个早期前提——这些约束正是让你能在不导致衰退或架构漂移的情况下保持速度的保障。

在实践中，我们用自定义 linter 和结构测试，外加一小套"品味不变量"来强制执行这些规则。例如，我们通过自定义 lint 静态强制结构化日志记录、Schema 和类型的命名规范、文件大小限制，以及平台特定的可靠性要求。由于这些 lint 是自定义的，我们将错误消息编写为向智能体上下文注入修复指导。

在以人类为中心的工作流中，这些规则可能会显得迂腐或令人束缚。而对智能体而言，它们成为了**倍增器**：一旦编码完成，便在所有地方同时生效。

与此同时，我们也明确区分了约束重要的地方和不重要的地方。这类似于领导一个大型工程平台组织：集中强制执行边界，在本地允许自主。你对边界、正确性和可重现性高度在意；在这些边界之内，你允许团队——或智能体——在解决方案的表达方式上拥有相当大的自由度。

最终生成的代码并不总是符合人类的风格偏好，这没关系。只要输出正确、可维护，且对未来的智能体运行可读，就达到了标准。

人类的品味被持续反馈回系统中。代码审查意见、重构 PR 和面向用户的 Bug，被捕获为文档更新或直接编码进工具中。当文档不足以表达时，我们将规则提升为代码。

## 吞吐量改变了合并理念

随着 Codex 吞吐量的提升，许多传统工程规范变得适得其反。

仓库以最小化阻塞性合并门槛运作。Pull Request 存续时间很短。测试不稳定问题通常通过后续的再次运行来解决，而非无限期地阻塞进度。在一个智能体吞吐量远超人类注意力的系统中，修正是廉价的，而等待是昂贵的。

在低吞吐量的环境中，这样做会是不负责任的。在这里，它往往是正确的权衡。

## "智能体生成"究竟意味着什么

当我们说代码库由 Codex 智能体生成时，我们指的是代码库中的**一切**。

智能体负责产出：

- 产品代码和测试
- CI 配置和发布工具
- 内部开发者工具
- 文档和设计历史
- 评估测试套件
- 代码审查意见和回复
- 管理仓库自身的脚本
- 生产环境仪表盘定义文件

人类始终在回路中，但工作的抽象层级与以往不同。我们负责排定工作优先级，将用户反馈转化为验收标准，并验证结果。当智能体遇到困难时，我们将其视为一个信号：识别缺少什么——工具、护栏、文档——然后将其反馈回仓库，始终让 Codex 本身来编写修复方案。

智能体直接使用我们的标准开发工具。它们拉取审查反馈、在行内回复、推送更新，并经常自行合并自己的 Pull Request。

## 持续提升的自主水平

随着越来越多的开发循环被直接编码进系统——测试、验证、审查、反馈处理和错误恢复——仓库最近越过了一个有意义的门槛：Codex 现在可以端到端地驱动一个新功能的开发。

给定一个提示词，智能体现在可以：

1. 验证代码库的当前状态
2. 复现一个已报告的 Bug
3. 录制一段演示故障的视频
4. 实现修复方案
5. 通过驱动应用来验证修复效果
6. 录制第二段演示问题已解决的视频
7. 提交 Pull Request
8. 回应智能体和人类的反馈
9. 检测并修复构建失败
10. 仅在需要判断力时才升级给人类处理
11. 合并变更

这些行为高度依赖于该仓库的特定结构和工具链，在没有类似投入的情况下，不应假设可以普遍迁移——至少目前还不行。

## 熵与垃圾回收

完全的智能体自主性也带来了新型问题。Codex 会复制仓库中已存在的模式——即使是那些不均匀或次优的模式。随着时间推移，这不可避免地导致漂移。

起初，人类手动解决这个问题。我们的团队曾经每周五（即一周 20% 的时间）专门清理"AI 糟粕"。不出所料，这无法规模化。

为此，我们开始将我们称之为"黄金原则"的内容直接编码进仓库，并构建了一套定期清理流程。这些原则是固执己见的、机械化的规则，使代码库对未来的智能体运行保持可读性和一致性。例如：

1. 我们倾向于使用共享工具包而非手工封装的 helper，以保持不变量的集中管理。
2. 我们不以"YOLO 风格"探测数据——我们在边界处进行验证或依赖有类型的 SDK，以防止智能体意外地基于猜测的结构进行开发。

我们定期运行一组后台 Codex 任务，扫描偏差、更新质量评级并提交有针对性的重构 PR。其中大多数可以在不到一分钟内审查完毕并自动合并。

这就像**垃圾回收**一样运作。技术债务如同高利贷：持续以小额增量偿还，几乎总是优于让其复利积累、最终在痛苦的突击中一次性清偿。人类的品味被捕获一次，然后在每一行代码上持续强制执行。这也让我们能够每天发现并解决不良模式，而不是让它们在代码库中扩散数日乃至数周。

## 我们仍在学习的内容

这一策略迄今为止运转良好，直至 OpenAI 内部正式发布并被采纳。为真实用户构建真实产品，帮助我们将投入锚定在现实中，并引导我们走向长期可维护性。

我们尚不清楚的是，在一个完全由智能体生成的系统中，架构内聚性如何随着数年时间的推移而演变。我们仍在学习人类判断力在哪里能带来最大的杠杆，以及如何将这种判断力编码为可复利的形式。我们也不知道这个系统在模型持续变得更强大的过程中将如何演进。
